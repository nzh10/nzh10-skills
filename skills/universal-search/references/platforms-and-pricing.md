# 各平台检索特性、计费与外部服务选型细则

## 一、微信公众号 (`wechat_search` + `web_fetch`)

- `wechat_search` 单次 ¥0.05（库内搜索 ¥0.02），约为网页搜索的十倍；专门覆盖普通网页索引缺失的中文内容：长文、垂直账号、一手体验、深度访谈、行业观察与近期发布。
- 当问题需要作者原话、具体细节或中文一手视角，而网页只有转载与摘要时，优先用 `wechat_search`；若官方文档、代码仓、英文资料、快讯或已知 URL 即可回答，用免费工具或 `web_search` 更快更省。
- 先发宽查询，再按结果收窄；通常第 1 页即够定位，翻页单独计费。正文用 `web_fetch` 读取（必须原样传入带 `&chksm=...#rd` 的完整链接，不可删减查询参数）；若仍命中微信验证页则同一链接不重抓，拿标题用 `web_search` 搜一次找官网或同名转载（不加作者或 `site:`，一个标题只搜一次，整轮补查不超过 2 个标题；拿到 1–2 篇完整数据正文即停手交付）。

## 二、抖音、小红书与 B 站 (`social_search` + `social_fetch`)

- `social_search` 覆盖抖音和小红书，`social_fetch` 读取抖音、小红书、B 站三个平台的作品正文。
- 小红书在常规网页索引中极薄，`site:xiaohongshu.com` 往往返回空结果，应直接走 `social_search`；拿到候选后优先抓摘要带具体读数的笔记，第 1 批已够回答问题时不再追加第 2 批抓取（总付费调用控制在 6 次内），正文中无目标指标的笔记直接剔除不列入交付。
- B 站视频页对常规 `web_fetch` 不友好，搜索可先用 `web_search`，正文统一走 `social_fetch`。
- 抖音翻页依赖上一页返回的游标（`cursor` / `search_id`），必须按顺序翻页，跳页会从头重算。
- 短链（`b23.tv`、`v.douyin.com`、`xhslink.com`）先用 `curl -Ls -o /dev/null -w '%{url_effective}'` 展开为标准作品链接后再传给 `social_fetch`。
- 工具不可用（缺凭据、接口报错、空结果）本身就是需要直接报告的事实；切换渠道前先确认新渠道确实覆盖目标来源。

## 三、单价参考与缓存机制

- **参考单价**（以实际账单与工具返回状态栏为准）：
  - `web_search` / `web_fetch`：约 ¥0.005 / 次
  - `wechat_search`：公众号搜一搜 ¥0.05 / 次，库内搜索 ¥0.02 / 次
  - 小红书搜索与详情：每页 $0.005
  - 抖音与 B 站：每次 $0.0005
- **会话缓存**：同一会话内相同请求自动复用缓存，强制刷新（`force=true`）会重新计费。缓存命中返回索引与本地文件路径（`fullOutputPath` / `recordPath`）；上下文压缩或重载后优先读取本地缓存文件，仅当临时文件已被清理时才重新抓取。

## 四、外部服务比价与选型对比细则

当任务明确要求做外部 API、SaaS 或数据供应商选型比价时（单纯阅读某个指定代码仓或 `llms.txt` 时不主动外拓抓第三方计费站）：
- **比较范围**：只比较用户划定范围内、且具备实际可调用接口的选项。
- **「尽量少」的含义**：在覆盖全部已定优先级的前提下减少供应商家数；若单家无法覆盖全部场景（如历史窗口限制），直接给出最简多家组合。
- **链接失效必须同站追查确认**：若用户给出的具体计费页路径失效、重定向或返回 0 字节空壳（例如旧版 `/Member/Price`），**绝不能直接标「不能确认」就跳过该家草率定方案**；应立即读取该供应商官网首页、站内导航/帮助文档或做一次 `site:<域名>` 搜索，定位现行官方价格页（如 `/Home/Price`）确认其真实产品形态（有无开放 API、会员价或按次价）。
- **事实归属清晰**：报价严格出自实际打开并读到正文的官方页面（注明原链接为空、实价取自哪一现行官方页面），若全站均被拦截无法打开才如实标注未取得，绝不凭记忆瞎猜；用户已给出的内部商务协议价或已知事实直接采用，不花钱联网质疑用户给定的内部条件。
